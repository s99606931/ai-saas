## 1. Executive Summary (CTO 종합 의견)

28개 MTU로 분해된 마스터 로드맵은 공공기관 SaaS 시장의 핵심 규제(CSAP, N2SF, ISMS-P)를 체계적으로 커버하며, 2026년 시장조사 결과(MCP, Policy as Code, SBOM, OSCAL)를 적시에 반영한 전략적으로 우수한 로드맵입니다. 다만, Phase 2~3 간 일정 중첩(M5~M7)으로 인한 병목 리스크, ISMS-P 101항목 신규 추가에 따른 Phase 2 과부하, 그리고 온프레미스 LLM이 기존 Plan의 "외부 서비스 연동만" 원칙과 충돌하는 범위 불일치가 조건부 승인의 근거입니다. 아래 6개 권장 수정 사항을 반영한 후 최종 승인을 권고합니다.

### 2.2 MTU 분해 상세 평가

**적정 MTU (22개)**: MTU-F1~F5, MTU-C1~C5, MTU-C7, MTU-C8, MTU-I1~I4, MTU-A1, MTU-A2, MTU-A5, MTU-A6, MTU-E1, MTU-E3

이 MTU들은 "1~2 세션 완료, 단일 책임, 즉시 검증" 원칙을 잘 준수합니다.

**과대 MTU (3개)** -- 분할 권장:

| MTU ID | 현재 크기 | 문제점 | 권장 조치 |
|--------|---------|--------|---------|
| MTU-C2 (D01~D07) | 7 파일 | 7개 분야를 한 MTU에 묶으면 2세션 초과 가능 | MTU-C2a (D01~D04, 관리/조직/인적/자산) + MTU-C2b (D05~D07, 공급망/침해/재해)로 분할 |
| MTU-C6 (ISMS-P) | 3 파일, 101항목 | CSAP 79항목과의 교차 매핑 작업만으로 1세션 소요 | MTU-C6a (체크리스트 + 매핑) + MTU-C6b (증적 자동화 + 자가진단)로 분할 |
| MTU-A3 (감리 T03~T06) | 9 파일 | 감리 4종 산출물 + 5단계 체크리스트는 명백히 3세션 이상 | MTU-A3a (T03~T04 설계서) + MTU-A3b (T05~T06 시험서) + MTU-A3c (5단계 체크리스트)로 분할 |

**과소 MTU (1개)**:

| MTU ID | 현재 크기 | 문제점 | 권장 조치 |
|--------|---------|--------|---------|
| MTU-F6 (CC 하네스 검증) | "기존" | 파일 수 미명시, 검증 기준이 Q-Gate G1~G3로 모호 | 기존 하네스 구성이 이미 완료되어 있으므로, MTU-F3와 병합하거나 검증 대상 파일 목록을 명시적으로 기재 |

분할 반영 시 총 MTU 수: 28개 -> 32~33개. MTU 평균 크기가 더 균일해지며, 1~2 세션 원칙 준수율이 향상됩니다.

### 2.3 Phase 순서 및 의존성 평가

**양호한 점**:
- 참조 기반 레이어(MTU-F2) -> CSAP 원천(MTU-C1) -> N2SF 매핑(MTU-C4) -> AI 게이트웨이(MTU-A1) 순서는 단방향 참조 원칙과 정합
- 의존성 그래프가 명시적이며, 순환 참조 없음
- Phase 1에서 기반 문서 + CC 하네스를 선행하는 것은 올바른 판단

**우려 사항**:

| 이슈 | 상세 | 영향도 |
|------|------|--------|
| Phase 2-3 중첩 (M5~M7) | Phase 2는 M3~M6, Phase 3는 M5~M7로 2개월 중첩. MTU-C7(Policy as Code)은 MTU-I1(k3s)에 의존하지만 두 MTU가 서로 다른 Phase에 속함 | High |
| MTU-I1 Phase 불일치 | 로드맵에서 Phase 3 Infrastructure (M5~M7)로 분류되었으나, Plan 원문은 Phase 2 (M6)에 k3s를 배치. MTU-C7이 MTU-I1에 의존하므로 MTU-I1은 Phase 2 초반에 완료되어야 함 | High |
| MTU-E2 (문서 포털) 의존성 과다 | "모든 MTU 완료" 의존은 비현실적. 68개 파일 중 70%+ 완료 시점에 포털 구축 착수 가능 | Low |

### 2.4 12개월 현실성 평가

**Phase별 작업량 분석**:

| Phase | 기간 | MTU 수 | 총 파일 수 | 월간 파일 수 | 현실성 |
|-------|------|--------|----------|-----------|--------|
| Phase 1 (M1~M2) | 2개월 | 6 MTU | ~17 | 8.5/월 | 양호 |
| Phase 2 (M3~M6) | 4개월 | 8 MTU | ~31 | 7.8/월 | 과밀 (ISMS-P 추가) |
| Phase 3 (M5~M7) | 3개월 | 5 MTU | ~16 | 5.3/월 | 양호 |
| Phase 4 (M7~M10) | 4개월 | 6 MTU | ~22 | 5.5/월 | 양호 |
| Phase 5 (M10~M12) | 3개월 | 3 MTU | 포털+α | 가변 | 리스크 있음 |

**핵심 병목**: Phase 2가 ISMS-P 101항목(MTU-C6), Policy as Code(MTU-C7) 신규 추가로 인해 기존 Plan 대비 약 40% 작업량 증가. 4개월 내 8 MTU 소화가 1인 또는 소규모 팀에서 가장 높은 일정 리스크입니다.

**권장**: Phase 2 기간을 M3~M7 (5개월)로 1개월 확장하고, Phase 3 시작을 M7로 조정. 또는 ISMS-P(MTU-C6)를 Phase 3으로 이동 (아래 권장 수정 사항 참조).

## 3. 기술 아키텍처 평가

### 3.1 k3s + Flux + Kyverno + OPA 조합 평가

| 평가 항목 | 판정 | 근거 |
|---------|------|------|
| 공공기관 환경 적합성 | 적합 | k3s는 리소스 제약 환경(WSL2) 최적화. Flux는 폐쇄망/Air-gapped 환경에 ArgoCD보다 우수 (외부 웹 UI 불필요) |
| Kyverno + OPA 하이브리드 | 적합 (권장) | 단순 정책(CSAP-D08 계정 통제, D11 컨테이너 불변성)은 Kyverno(Kubernetes 네이티브, 학습 비용 최소), 복잡 정책(N2SF 등급별 Namespace 격리, 교차 정책)은 OPA/Gatekeeper(Rego DSL) |
| 운영 복잡도 | 주의 | Kyverno + OPA 동시 운영은 정책 충돌 가능성 존재. MTU-C7에 **충돌 해결 전략 섹션** 추가 권장 |
| CSAP D-11 정합성 | 적합 | CIS Kubernetes Benchmark x CSAP-D11 매핑이 MTU-I1에 포함되어 있어 k3s 보안 기본값 보장 |

**CTO 판정**: k3s + Flux + Kyverno + OPA 조합은 공공기관 폐쇄망 환경에 최적. Harbor 추가(MTU-I3)로 이미지 취약점 스캔 + Sigstore 서명까지 커버하면 공급망 보안 체계가 완결됩니다.

### 3.2 하이브리드 LLM 전략 (온프레미스 + 외부 API) 평가

| 평가 항목 | 판정 | 근거 |
|---------|------|------|
| N2SF 정합성 | 정합 | C/S등급 -> 온프레미스 Llama 3.1, O등급 -> Claude API. N2SF N-05 (데이터 영역) 완전 준수 |
| 기존 Plan과의 일관성 | **불일치** | Plan 섹션 2.2 제외 범위에 "AI/LLM 로컬 구현 (외부 서비스 연동만)" 명시. 온프레미스 LLM 가이드(MTU-A1)는 이를 확장하므로 Plan 업데이트 필요 |
| 실현 가능성 | 조건부 | Llama 3.1 8B는 WSL2 환경에서 구동 가능(16GB+ RAM 필요)하나, 70B 모델은 전용 GPU 서버 필요. 가이드 문서 범위에서 하드웨어 전제조건 명시 필수 |
| 차별화 기여도 | 높음 | 글로벌 솔루션(Vanta, Drata)은 온프레미스 LLM 가이드 없음. N2SF C/S등급 데이터를 AI로 처리할 수 있는 유일한 방법 |

**CTO 판정**: 하이브리드 LLM 전략은 N2SF 완전 준수를 위해 필수적이나, 기존 Plan의 "외부 서비스 연동만" 범위와 충돌합니다. Plan 문서의 제외 범위(섹션 2.2)를 수정하여 "온프레미스 LLM 설치 가이드는 In Scope에 포함 (단, LLM 커스터마이징/파인튜닝은 Out of Scope)"으로 조정 필요합니다.

### 3.3 OSCAL 호환성 레이어 평가

| 평가 항목 | 판정 | 근거 |
|---------|------|------|
| 범위 적정성 | 적정 (과도하지 않음) | FedRAMP가 2026년 9월 OSCAL 의무화. 한국은 아직 미의무이나, CSAP 79항목 -> OSCAL 포맷 변환만으로 범위 제한 (2파일, 1 MTU). 과도하지 않음 |
| 전략적 가치 | 높음 | 한국 선제 대응 + 국제 입찰 참여 시 FedRAMP 동등성 주장 가능. "OSCAL 호환"은 마케팅 차별화 포인트 |
| 우선순위 적정성 | 적정 (P1) | Phase 4 배치가 적절. P0로 올릴 필요 없음 |
| 리스크 | 낮음 | MTU-A6은 2파일, 1세션. MTU-C1의 CSAP-DXX-YY ID가 OSCAL `control.id` 매핑 기반이 되므로 MTU-C1 설계 시 OSCAL 호환 필드를 사전 반영(이미 MTU-C1 Plan에 반영됨) |

**CTO 판정**: OSCAL 레이어는 필수입니다. 단, MTU-C1(마스터 체크리스트) 설계 시 OSCAL 호환 메타데이터(control.props)를 처음부터 포함하는 것이 핵심이며, 이 점은 이미 MTU-C1 Plan에 반영되어 있어 양호합니다.

## 4. 리스크 Top 3 + 완화 방안

### Risk 1: Phase 2 과부하 (일정 리스크) -- 심각도: High

**설명**: Phase 2 (M3~M6)에 기존 CSAP 79항목(MTU-C1~C5) + 신규 ISMS-P 101항목(MTU-C6) + Policy as Code(MTU-C7) + Supply Chain(MTU-C8)이 집중. 8개 MTU가 4개월에 배치되어 있으며, ISMS-P 101항목의 CSAP 교차 매핑 작업만으로도 1주 이상 소요 예상.

**영향**: Phase 2 지연은 Phase 3~5 전체 일정을 후방 압박. 12개월 목표 미달 가능성.

**완화 방안**:
1. **MTU-C6(ISMS-P)를 Phase 3 초반(M7)으로 이동**. 근거: ISMS-P 의무화는 2027년 7월이므로 M7 완료(2026년 10월)로도 6개월+ 여유. CSAP 79항목이 우선
2. Phase 2 기간을 M3~M7 (5개월)로 확장, Phase 3을 M7~M9로 조정
3. MTU-C2, MTU-C6을 분할(상기 2.2 참조)하여 병렬 작업 가능성 확보

### Risk 2: N2SF 2026년 기준 변경 (규제 리스크) -- 심각도: High

**설명**: N2SF는 2026년 본격 시행되며, 국정원 세부 가이드라인이 연중 업데이트될 가능성이 높습니다. Plan Gap-4에서 이미 식별되었으나, 구체적인 모니터링 + 자동 대응 메커니즘이 미비합니다.

**영향**: Module 3(N2SF) 전체 재작성 가능성. MTU-C4(N2SF 매핑), MTU-C5(N2SF 영역), MTU-I5(레퍼런스 아키텍처)에 직접 영향.

**완화 방안**:
1. **N2SF 모니터링 담당 MTU 신설 (MTU-F7 또는 운영 프로세스)**:
   - 국정원 가이드라인 업데이트 RSS/공지사항 주간 확인
   - 변경 발생 시 30일 이내 영향 분석 + 업데이트 (NFR-7 기준)
2. Module 3 문서에 **버전 격리 전략** 적용:
   - `03-n2sf/grade-classification-guide.md`에 "적용 기준일: YYYY-MM-DD" 메타데이터 추가
   - 기준 변경 시 신규 버전 파일 생성 (기존 파일 보존)
3. MTU-C4(N2SF 매핑) 내에 "미확정 항목" 섹션을 두고, 확정 시점까지 TBD로 관리

### Risk 3: MTU-A1 (AI 게이트웨이 + MCP + 온프레미스 LLM) 범위 확대 -- 심각도: Medium-High

**설명**: MTU-A1은 원래 AI 보안 게이트웨이(FR-6.1, FR-6.2, FR-6.3)만 담당했으나, 시장조사 반영으로 MCP 통합 + 온프레미스 LLM 가이드가 추가되어 4파일로 확대. 기존 Plan의 Out of Scope("AI/LLM 로컬 구현")와 충돌하며, 2세션 이내 완료가 어려울 수 있습니다.

**영향**: 범위 크립(scope creep) 패턴. Plan-Design-Roadmap 간 일관성 훼손은 감리 지적 사항이 될 수 있음.

**완화 방안**:
1. **MTU-A1을 2개로 분할**:
   - MTU-A1a: AI 보안 게이트웨이 (기존 FR-6.1~6.3) + MCP 통합 패턴
   - MTU-A1b: 온프레미스 LLM 가이드 (신규, 하드웨어 전제조건 명시)
2. Plan 문서(섹션 2.2) 업데이트: "AI/LLM 로컬 구현" 제외 범위를 "온프레미스 LLM 설치 가이드(구성/연동)는 In Scope, 모델 커스터마이징/파인튜닝은 Out of Scope"으로 조정
3. Design 문서 Context Anchor의 SCOPE도 동시 업데이트
