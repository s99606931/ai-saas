## 분야 개요

침해사고 관리는 보안 사고의 **탐지, 분석, 대응, 복구, 보고** 전 과정을 체계적으로 관리하는 운영/기술 통제입니다. 공공기관 SaaS는 KISA 신고 의무와 이용기관 통보 의무가 있으므로 신고 체계를 반드시 포함해야 합니다.

**핵심 키워드**: 침해사고 대응 절차, 보안 이벤트 모니터링, 감사 로그, 보고 체계, 사후 분석

**연계 MTU**:
- ECC 하네스: `audit.jsonl` 감사 로그 (CSAP-D06-03 자동 충족)
- MTU-I4 네트워크/OpenTelemetry: 보안 이벤트 수집 인프라
- MTU-A6 준수 현황 대시보드: 실시간 보안 모니터링 연계

## CSAP-D06-01: 침해사고 대응 절차

> **중요도**: 상 | **구분**: 필수

### 구현 목표

침해사고 탐지/분석/복구/보고 4단계 절차서를 수립하고 대응 팀을 구성한다.

### 구현 방법

**침해사고 대응 5단계 프로세스**

```
단계 1: 탐지 (Detection)
    │  보안 이벤트 모니터링, IDS/IPS 경보, audit.jsonl 이상 탐지
    ▼
단계 2: 분석 (Analysis)
    │  사고 유형 분류, 영향 범위 확인, 심각도 판단
    ▼
단계 3: 억제 (Containment)
    │  피해 확산 방지, 네트워크 격리, 계정 잠금
    ▼
단계 4: 복구 (Recovery)
    │  시스템 복원, 패치 적용, 서비스 재개
    ▼
단계 5: 사후 분석 (Post-Incident)
    │  원인 분석, 재발 방지, 교훈 기록
    ▼
    [보고/신고: KISA, 이용기관, 경영진]
```

**심각도 분류 기준**

| 등급 | 기준 | 대응 시한 | 보고 경로 |
|------|------|---------|---------|
| Critical | 개인정보 유출, 서비스 전면 중단, 시스템 탈취 | 즉시 | 담당자 -> CISO -> 경영진 -> KISA (24시간 내) |
| High | 데이터 무결성 침해, 주요 서비스 일부 중단 | 4시간 | 담당자 -> CISO -> 경영진 |
| Medium | 비정상 접근 시도, 악성코드 탐지 (격리 완료) | 24시간 | 담당자 -> CISO |
| Low | 정책 위반 (경미), 스팸/피싱 시도 | 72시간 | 담당자 -> 팀장 |

**대응 팀 구성 (CSIRT)**

| 역할 | 책임 | 비상 연락 |
|------|------|---------|
| 침해사고 대응 팀장 | 전체 대응 지휘, 경영진 보고 | [비상 연락망 참조] |
| 보안 분석가 | 사고 분석, 포렌식, 증거 수집 | [비상 연락망 참조] |
| 시스템 운영자 | 시스템 격리/복구, 패치 적용 | [비상 연락망 참조] |
| 네트워크 관리자 | 네트워크 격리, 방화벽 긴급 규칙 | [비상 연락망 참조] |
| 법무/대외 | KISA 신고, 이용기관 통보, 법적 조치 | [비상 연락망 참조] |

### 필요 증거 자료

| 증거 | 형태 | 보관 위치 |

## CSAP-D06-02: 보안 이벤트 모니터링

> **중요도**: 상 | **구분**: 기술(필수)

### 구현 목표

보안 로그 수집 체계를 구축하고 실시간 모니터링을 수행한다.

### 구현 방법

**단계 1: 로그 수집 대상 정의**

| 로그 소스 | 수집 항목 | 수집 방법 |
|---------|---------|---------|
| 애플리케이션 | audit.jsonl (인증, 권한, CRUD) | ECC 하네스 자동 기록 |
| 웹서버 | 접근 로그, 에러 로그 | Nginx/Caddy 로그 전달 |
| 데이터베이스 | 쿼리 로그, 접근 로그 | DB 감사 기능 활성화 |
| 운영체제 | 시스템 로그, 보안 이벤트 | journald, syslog |
| 네트워크 | 방화벽 로그, IDS/IPS 이벤트 | 네트워크 장비 syslog |
| k3s 클러스터 | Pod 이벤트, API 서버 감사 | Kubernetes audit log |

**단계 2: audit.jsonl 연동 패턴**

ECC 하네스의 `audit.jsonl`은 CSAP-D06-02 보안 이벤트 모니터링의 핵심 로그입니다:

```typescript
// audit.jsonl 이벤트 구조 (ECC 하네스 기본 제공)
interface AuditEvent {
  timestamp: string       // ISO 8601
  actor: string           // 수행자 ID
  action: string          // 'LOGIN' | 'LOGOUT' | 'ACCESS_DENIED' | 'DATA_EXPORT' | ...
  target: string          // 대상 리소스
  result: 'success' | 'failure'
  ip: string              // 클라이언트 IP
  metadata?: Record<string, unknown>
}

// 보안 이벤트 기록 예시
import { appendFileSync } from 'fs'

function auditLog(event: AuditEvent): void {
  const entry = JSON.stringify({
    ...event,
    timestamp: new Date().toISOString(),
  })
  appendFileSync('.claude/audit.jsonl', entry + '\n')
}

// 사용 예: 비정상 접근 시도 기록
auditLog({
  actor: userId,
  action: 'ACCESS_DENIED',
  target: '/api/admin/users',
  result: 'failure',
  ip: clientIP,
  metadata: { reason: 'insufficient_permissions', role: 'viewer' }
})
```

**단계 3: 이상 탐지 규칙**

| 탐지 규칙 | 조건 | 심각도 | 대응 |
|---------|------|-------|------|
| 무차별 대입 공격 | 동일 IP 10분 내 로그인 실패 5회+ | High | IP 차단 + 알림 |
| 비인가 접근 시도 | 권한 없는 리소스 접근 시도 3회+ | Medium | 계정 잠금 검토 + 알림 |
| 비정상 시간 접근 | 업무 시간 외(22:00~06:00) 관리자 접근 | Medium | CISO 알림 |
| 대량 데이터 반출 | 1시간 내 1,000건+ 데이터 조회 | High | 계정 잠금 + 조사 |
| 관리자 권한 변경 | 관리자 계정 권한 변경 이벤트 | Critical | 즉시 알림 + 확인 |

### 필요 증거 자료

| 증거 | 형태 | 보관 위치 |
|------|------|---------|
| 로그 수집 구성도 (SIEM) | 구성도 | 문서관리시스템 |
| 로그 수집 현황 (소스별) | 현황표 | 모니터링 대시보드 |
| 이상 탐지 규칙 목록 | 설정 문서 | 보안운영센터 |
| 모니터링 대시보드 화면 | 스크린샷 | 문서관리시스템 |

## CSAP-D06-03: 감사 로그 보관

> **중요도**: 상 | **구분**: 기술(필수)

### 구현 목표

감사 로그를 최소 1년 이상 보관하고 append-only 무결성을 보장한다.

### 구현 방법

**단계 1: 로그 보관 정책**

| 항목 | 정책 | 근거 |
|------|------|------|
| 최소 보관 기간 | 1년 (권장 3년) | CSAP-D06-03, 개인정보보호법 |
| 무결성 보장 | append-only (수정/삭제 불가) | CSAP-D06-03 |
| 암호화 | 저장 시 AES-256 암호화 | CSAP-D09-02 |
| 접근 통제 | 읽기: 보안 담당자, 감사인 / 쓰기: 시스템만 | CSAP-D08 |
| 백업 | 별도 스토리지에 일일 백업 | CSAP-D07-02 |

**단계 2: audit.jsonl append-only 보장 패턴**

```bash
# Linux: 파일에 append-only 속성 설정 (immutable append)
sudo chattr +a /path/to/audit.jsonl

# 확인
lsattr /path/to/audit.jsonl
# 결과: -----a--------e---- /path/to/audit.jsonl

# k3s 환경: PersistentVolume에 로그 저장
# - ReadWriteOnce 모드
# - 별도 StorageClass (삭제 보호)
```

```typescript
// audit.jsonl 무결성 검증 (해시 체인)
import { createHash } from 'crypto'

function appendAuditLog(entry: AuditEvent, prevHash: string): string {
  const entryWithHash = {
    ...entry,
    prevHash,
    hash: '', // placeholder
  }
  const hash = createHash('sha256')
    .update(JSON.stringify({ ...entryWithHash, hash: undefined }) + prevHash)
    .digest('hex')
  entryWithHash.hash = hash

  appendFileSync('.claude/audit.jsonl', JSON.stringify(entryWithHash) + '\n')
  return hash
}
```

**단계 3: 로그 아카이빙**

```
일간: audit.jsonl → 날짜별 파일 분리 (audit-2026-04-05.jsonl)
월간: 월별 아카이브 압축 + 해시 서명
분기: 분기별 무결성 전수 검증 (해시 체인 확인)
연간: 1년 초과 로그 별도 아카이브 스토리지 이동
```

### 필요 증거 자료

| 증거 | 형태 | 보관 위치 |
|------|------|---------|
| 로그 보관 정책서 | PDF/문서 | 문서관리시스템 |
| append-only 설정 증빙 (chattr/설정) | 스크린샷/설정 | 서버 관리 시스템 |
| 로그 스토리지 설정 (용량, 보관 기간) | 설정 문서 | 인프라 관리 |
| 해시 체인 무결성 검증 결과 | 검증 보고서 | 문서관리시스템 |

## CSAP-D06-04: 보안 사고 보고 체계

> **중요도**: 상 | **구분**: 필수

### 구현 목표

사고 발생 시 보고 경로(담당자->CISO->경영진->KISA)와 비상 연락망을 수립한다.

### 구현 방법

**보고 체계 흐름도**

```
보안 사고 탐지
    │
    ▼
침해사고 대응 담당자
    │ (30분 이내 초기 보고)
    ▼
CISO (정보보호 최고책임자)
    │ (심각도 판단)
    │
    ├── Critical/High ─────────────────────┐
    │   (4시간 이내)                        │
    │                                      ▼
    │                              경영진 (대표이사/기관장)
    │                                      │
    │                              ┌───────┼───────┐
    │                              ▼       ▼       ▼
    │                           KISA    이용기관   관계기관
    │                        (24시간내) (4시간내) (필요 시)
    │
    └── Medium/Low
        (24시간 이내 정기 보고)
```

**신고 기관별 절차**

| 신고 대상 | 신고 기한 | 신고 방법 | 연락처 |
|---------|---------|---------|-------|
| KISA (한국인터넷진흥원) | 24시간 이내 | KISA 118 또는 온라인 신고 | 118, https://www.boho.or.kr |
| 개인정보보호위원회 | 72시간 이내 (개인정보 유출 시) | 온라인 신고 | https://www.pipc.go.kr |
| 이용기관 (공공기관) | 4시간 이내 | 서면 + 유선 통보 | 계약서 상 연락처 |
| 경찰청 사이버수사국 | 필요 시 | 온라인 신고 | https://ecrm.police.go.kr |

**보고서 양식 필수 항목**

| 항목 | 내용 |
|------|------|
| 사고 일시 | 최초 탐지 시각, 사고 추정 시각 |
| 사고 유형 | 해킹, 악성코드, 내부자 위협, DDoS 등 |

| 예상 복구 시간 | RTO 기반 복구 예상 시간 |
| 추가 조치 계획 | 향후 대응 계획 |

## CSAP-D06-05: 사고 후 분석

> **중요도**: 중 | **구분**: 필수

### 구현 목표

침해사고 후 원인 분석, 재발 방지 대책을 수립하고 교훈을 기록한다.

### 구현 방법

**단계 1: 사후 분석 보고서(Post-mortem) 작성**

| 섹션 | 내용 |
|------|------|
| 사고 개요 | 사고 유형, 일시, 영향 범위 요약 |
| 타임라인 | 사고 발생부터 완전 복구까지 시간순 기록 |
| 근본 원인 | 5-Why 분석 또는 어항 다이어그램(Fishbone) 기법 |
| 대응 평가 | 대응 절차 준수 여부, 대응 시간 적정성, 개선점 |
| 재발 방지 대책 | 기술적/관리적/운영적 개선 조치 |
| 교훈 (Lessons Learned) | 향후 유사 사고 대응 개선 사항 |
| 후속 조치 일정 | 개선 조치별 담당자, 기한, 완료 여부 |

**단계 2: 재발 방지 대책 유형**

| 유형 | 대책 예시 |
|------|---------|
| 기술적 | 취약점 패치, 방화벽 규칙 강화, IDS 규칙 추가, 암호화 강화 |
| 관리적 | 보안 정책 개정, 접근 권한 재검토, 보안 교육 강화 |
| 운영적 | 모니터링 규칙 추가, 점검 주기 강화, 대응 절차 개선 |

**단계 3: 교훈 기록 및 공유**

```
교훈 기록 프로세스:

1. 사후 분석 회의 (사고 종료 후 1주일 이내)
   ├─ 참석: CSIRT 전원 + 관련 부서 담당자
   └─ 산출: 사후 분석 보고서 초안

2. 보고서 확정 (사고 종료 후 2주일 이내)
   ├─ CISO 검토 및 승인
   └─ 이용기관 최종 보고 (해당 시)

3. 교훈 공유 및 반영
   ├─ 보안 교육 자료 반영
   ├─ 대응 절차서 업데이트
   └─ 모니터링 규칙 갱신
```

### 필요 증거 자료

| 증거 | 형태 | 보관 위치 |
